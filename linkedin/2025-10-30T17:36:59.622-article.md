In IT, storing and moving data is a big challenge. Therefore when designing or upgrading your virtualization infrastructure you should focus on choosing a suitable approach to block #storage. In this post I will outline a short overview and some tricks that I recently discovered thanks to a post by Klara Inc.


For virtualization storage you ideally want something which avoids the time consuming moving of data when you need to live-migrate the virtual machine onto a different virtualization node. This allows to do some maintenance on the node you are evacuating or spin up the virtual machine elsewhere in general because the original node failed.


Traditional virtualization infrastructure typically relied on a SAN for storage and local storage was only used for the hypervisor. Everything else was on the big, expensive, but highly reliable SAN usually connected using FibreChannel network.


But a SAN and the replacement parts tends to be expensive and maybe you don't need all the fancy features. One approach is to just use a distributed storage system in a hyper-converged infrastructure, where the virtualization nodes are also storage nodes and agree among each other what data to store where. This works very well but it also tend to incur higher latency, because of all the agreements and synchronizations. That means processing a high number of small requests such as with databases might require careful consideration and might not be viable bellow a certain scale.


What if there was a good enough middle ground for small setups or special cases where you want a high number of operations and a shared storage but are limited on budget?


Suppose you just have two virtualization nodes with plentiful local storage. You export the storage as an iSCSI LUN on both nodes, the iSCSI targets. Now you can talk to the storage over regular TCP.

Inside of the VM you can do a mirrored storage over the LUNs as a software based RAID1. I suggest using OpenZFS but you can use dm-raid based approaches such as LVM or mdadm as well.


You should relax many of the reliability settings such as noop_out_interval, noop_out_timeout and replacement_timeout if you use Linux as the iSCSI initiator so if one node should fail you don't wait for it to come back online but basically use the rest of the LUNs to continue running the service – that's why you have the mirror in the first place. If the node came back because of e.g. a power outage it still contains most of the data unchanged. ZFS can detect that and in some cases just synchronize the difference. With dm-raid you would need to rewrite everything, which would be burdensome.


However dm-raid has one advantage, the write_mostly setting which is suitable when you have slow storage in one of the nodes and you want to convey that you only just want to make sure it contains all the data but if you can help it to use the other faster nodes for fast reads.
