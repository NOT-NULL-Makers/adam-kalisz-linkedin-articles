Let's find the total interaction count for a single user, `'user_75000'`. This requires **joining** the tables, **filtering** by `username`, and then **aggregating** the results.

EXPLAIN ANALYZE

**What happened this time?**

1.  It used an index on `users` to find the `id` for `'user_75000'`.
2.  Then, it used our new `idx_interactions_user_id` to perform an **Index Scan** on `user_interactions`, directly fetching only the 30 rows belonging to that specific user.

Prompt answer:

Yes, while PostgreSQL doesn't have a single command that automatically says, "You should add this specific index," it provides powerful tools to help you find slow queries that are prime candidates for indexing.

The core principle is to identify queries that perform a **Sequential Scan** on a large table where a `WHERE` or `JOIN` clause is filtering for a small subset of rows. These are the operations that benefit most from an index.

Here are the most common methods to find these queries.

-----

### 1\. The `pg_stat_statements` Extension 🕵️‍♂️

This is the most effective method for monitoring a live production database. The `pg_stat_statements` extension tracks execution statistics for all queries running on your server, allowing you to find the most resource-intensive ones.

#### How to use it:

**Step A: Enable the Extension**
You need to enable it in your `postgresql.conf` file and then create the extension in your database.

1.  Edit `postgresql.conf` and add `'pg_stat_statements'` to the `shared_preload_libraries` setting:
    ```ini
    shared_preload_libraries = 'pg_stat_statements'
    ```
2.  Restart the PostgreSQL server for the change to take effect.
3.  Connect to your database and run:
    ```sql
    CREATE EXTENSION pg_stat_statements;
    ```

**Step B: Find Expensive Queries**
You can now query the `pg_stat_statements` view. This query finds the top 10 queries by their total execution time:

```sql
SELECT
    (total_exec_time / 1000 / 60) AS total_minutes,
    mean_exec_time AS avg_ms,
    calls,
    query
FROM
    pg_stat_statements
ORDER BY
    total_exec_time DESC
LIMIT 10;
```

When you find a query in this list with a high `avg_ms` (average milliseconds) and a `Seq Scan` in its plan (which you'd check next with `EXPLAIN ANALYZE`), it's a strong candidate for an index on the columns used in its `WHERE` or `JOIN` clauses.

-----

### 2\. Logging Slow Queries

You can configure PostgreSQL to automatically write any query that takes longer than a specified time to the log file. This is a simpler, reactive approach.

#### How to use it:

1.  Edit your `postgresql.conf` file and set the `log_min_duration_statement` parameter. Setting it to `250ms`, for example, will log any query that takes 250 milliseconds or longer.
    ```ini
    log_min_duration_statement = '250ms'
    ```
2.  Reload the PostgreSQL configuration (no restart needed for this setting).
3.  Monitor your PostgreSQL log files. When a slow query appears, you can copy it and analyze it.

For example, your log might show:

```log
2025-09-15 10:06:15.123 CEST LOG:  duration: 1485.541 ms  statement: SELECT u.username, SUM(i.interaction_count) ...
```

This tells you exactly which query is slow. The next step is to run `EXPLAIN ANALYZE` on it to diagnose the cause.

-----

### 3\. Manual Analysis with `EXPLAIN ANALYZE` 🩺

This is the fundamental diagnostic tool. Once you've identified a potentially slow query (either from your application's performance or from the methods above), you run `EXPLAIN ANALYZE` to see its execution plan.

As we saw in the previous examples, you're looking for this smoking gun:

  * **`-> Seq Scan on your_large_table`**: This means the database is reading the entire table.
  * **`Filter: (your_column = 'some_value')`**: This shows a filter is being applied *after* reading the data, which is inefficient.

When you see these two together on a table with thousands or millions of rows, you've found a query that will almost certainly benefit from an index on `your_column`.

### Summary of the Workflow

1.  **Find:** Use `pg_stat_statements` or slow query logs to find your most resource-intensive queries.
2.  **Diagnose:** Run `EXPLAIN ANALYZE` on those specific queries to confirm they are using inefficient Sequential Scans.
3.  **Fix:** Add a `CREATE INDEX` statement on the relevant column(s) used in the `WHERE` clause or `JOIN` condition.
4.  **Verify:** Run `EXPLAIN ANALYZE` again to confirm PostgreSQL is now using a much faster **Index Scan**.
